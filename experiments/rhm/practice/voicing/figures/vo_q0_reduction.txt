  The learner writes `canon[f]` for a level-1 feature f. Its ear (the generator, the
  reader, both students of `bottom_map`) reads that back as
      g(f) = bottom_map[canon[f,0] + v*canon[f,1]] .
  Where g(f) != f the RECORD and the RECALL of the same write disagree at level 1,
  and the disagreement propagates up every tuple that contains f.

  `bottom_map` collisions on this draw (code -> the (feature, rule) pairs that write it): {12: [(1, 1), (4, 1)], 39: [(2, 0), (7, 0)]}
  A macro writes `canon[f]` = rule 0 ONLY, so a collision is reachable by a write
  exactly when two features collide on their rule-0 codes.
      code 12: writers [(1, 1), (4, 1)] -> rule-0 writers [] (not reachable)
      code 39: writers [(2, 0), (7, 0)] -> rule-0 writers [2, 7] (REACHABLE by a canonical write)

====================================================================================================
[V5] THE OFFLINE CEILING — what is cheap and what is not
====================================================================================================
  THE SPEC's FORM (a head fitted to the oracle's per-node repair set on the audition
  path, `embouchure`'s `own_verdict` analogue) IS NOT AVAILABLE OFFLINE HERE, and
  the reason is a property of the fork, not of effort:
    * the head's input is `trunk(core, obs)` — the pooled hiddens of the arm's OWN
      trained generator at that cycle. No banked tag carries the trunk's weights
      (the compact mirror is `results.json` + `entry*.json`), so there is no x to
      fit on.
    * the contexts are not banked either: `SpanExecutor._store` keeps them in memory
      and the log records only their COUNT (`span.buf` / `span.hold`).
    * `embouchure` could fit `own_verdict` offline because its head's input was a
      (feature, register) pair, not a learned representation, and its rows were in
      `spell_rows` on the volume.
  So the ceiling that is analogous here is an IN-RUN one (a `voicing` arm whose
  target is the repair set) and it belongs to Q1/Q2, not to Q0.

  WHAT IS CHEAP OFFLINE, and is computed instead — the TABLE-SIDE ceiling. Whatever
  the chooser is, it picks one row of the operative table. So per (level, node) the
  best any chooser could do is bounded by whether the table HOLDS a row whose token
  class contains a feature that repairs the instance. The gap between that bound and
  the instrument's `contains_rep` is what a better chooser could win; the rest is
  the book's.

  Computed on the run's own operative books. `features coverable` is the UNION of the
  token classes the book holds, against the alphabet v = 8. It is a property of the
  book, not a claim that all 8 are demanded at that node.

      cyc  L   rows  token classes in book  features coverable  of v=8  rows needed for full cover

      186 L3     89                      9                   7       8                          5
